# MaatruCare — final QA and polish report

**Updated 7 November 2026 · local branch `maatrucare-final-polish`**

## Executive summary

The repository and the prior QA fixes were preserved. The reported permission failures have concrete, non-bypass causes; the permission API now supports authorized missing grants and repeat-safe no-ops while preserving denial/conflict behavior. Frontend caregiver IDs are resolved from API results instead of a hard-coded mapping. The AI note allowlist is removed while server-side validation, a public-demo gate, provider-side credentials, rate limits, and human review remain. The existing app received a cohesive visual/accessibility polish. A scoped Lifestyle reset is opt-in, controller-authorized and covered by isolation tests. All code and screenshots are local; no production database, deployment settings, credentials, external account, push, or deployment were touched.

## Prioritized root causes and fixes

### P1 — `GET /caregivers` and `GET /tasks` return 403

Both backend routes require the `Coordination tasks` permission for the supplied `actor_caregiver_id`. The access service returns HTTP 403 (`Permission is not enabled`) when the actor has no matching permission record or the record is disabled. A fresh local synthetic seed enables this permission for caregiver 1, but database initialization seeds only an empty database and does not reconcile existing permissions. The checked-in seed therefore does not establish the state of the deployed database. The likely production causes are a missing/disabled grant or an actor/database mismatch; the exact live state remains unverified.

**Fix and safe action:** enforcement is unchanged. The authorized controller can now create a missing grant through the permission workflow. The frontend presents an actionable denial message and resolves actor/owner IDs using backend caregiver records. An authorized operator must confirm the production grant; do not reseed production or change actor IDs to conceal a 403.

### P1 — repeated permission PUTs return 409

The original route conflated no matching row and multiple matching rows into a uniqueness conflict, and it treated an already-satisfied state as an error. The causes are now distinct: authorized enable on a missing row creates the grant; an already-matching row returns its existing record; multiple rows remain a 409; revoking a nonexistent row remains a 409. Controller and target-caregiver authorization checks still run before mutation. Consent/Care Circle controls suppress duplicate in-flight submissions and synchronize feedback from the returned result.

### P2 — AI endpoint rejects all but synthetic allowlist notes

The endpoint previously compared normalized input against a fixed small set. That allowlist is removed. The endpoint now accepts varied 10–3000 character notes after heuristic email/phone/record-number and clinical-content screening; direct treatment/bleeding advice terms are rejected before the AI service. The server-side five-request-per-hour per-IP in-memory limiter, disabled-by-default public-demo switch, server-only `GEMINI_API_KEY` lookup, and `requires_human_review` response are preserved. The model instruction treats notes as untrusted data. Tests mock the provider; no real Gemini request was made.

### P2 — workflow/UI reliability and demo fidelity

Hard-coded frontend caregiver IDs could diverge from backend data. Task create/update/reassignment and handoff create/acknowledge/complete now resolve IDs from the loaded caregiver records; task owner changes clear the opposite owner field. Permission toggles block duplicate submissions. AI copy accurately describes draft/local review behavior, task reassignments call the existing API, and visible demo copy avoids implying that illustrative history or local review is verified/persisted. Global loading/error states and status announcements were improved. A warm sage design system, responsive/focus/motion treatments, and consistent semantic colors were applied without changing the app architecture.

### P2 — Lifestyle reset safety and stale demo state

The reset route is disabled unless `MAATRUCARE_DEMO_RESET_ENABLED=true`, then reuses existing controller authorization and only deletes Lifestyle logs belonging to the selected patient. Optional preferences reset is explicit; recommendations, routines and unrelated patient/care records are preserved. The backend transaction rolls back on failure and returns deletion counts; tests cover unauthorized/default-off cases, patient isolation, preservation, optional goals and repeat reset. Settings requires confirmation and, after success, links to the Lifestyle route, which refetches persisted state. The Lifestyle date now hydrates from the browser-local calendar rather than a build-time date.

## Remaining limitations and manual action

- The exact production permission state is unknown because the live Render database was not queried. An authorized controller should verify/grant `Coordination tasks` for the intended caregiver in the intended environment.
- AI provider generation has not been tested with a live Gemini credential. A live demo requires the operator to verify the server-side key and deliberately enable the public-demo gate; no deployment configuration was changed.
- Identifier/clinical text checks are heuristic, not a privacy guarantee. The rate limiter is in-memory and per process. The numeric actor ID/role checks in this demo do not establish authenticated identity; the current system is not appropriate for real patient records without identity, privacy, security, and deployment review.
- AI review buttons are local browser state and do not persist an audit record, create tasks, or share information. No clinical diagnosis, treatment recommendation, medical validation, HIPAA compliance, or certification is claimed.
- Lifestyle recording and reset are present in the current branch. They were tested only with synthetic data; the feature has not received clinical validation or external clinician review and must not be presented as diagnosis or treatment advice.
- Legacy deprecation warnings remain in backend dependencies and date handling; they were not changed in this minimal final pass.
